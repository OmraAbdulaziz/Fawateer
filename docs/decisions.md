# Decisions

Every important design decision and the reason for it. Use this page to answer the committee's "why did you do it this way?" questions.

All decisions below were approved on 2026-10-04 (plan version 3).

## Architecture and Data Flow

| Decision | Why |
|---|---|
| POS → Hub is **pull**: the Hub reads `NEW` invoices every 2 seconds | The POS is just a database (the supervisor's "update cycle" idea). 2 seconds keeps the full flow near 5 seconds. |
| Hub → Fawateer is **push** (HTTP POST) | Instant, which keeps the Zero-Touch promise. |
| The POS shows `SENT` for both forwarded and rejected invoices | The shop must not learn which of its customers use Fawateer. |
| No `FAILED` status and no retry; errors are logged | Servers are assumed to be up (CLAUDE.md §4). Retry is out of scope. |
| The Hub and the backend each have their own copy of the receipt JSON classes | In real life they are different organizations. They share only a JSON contract, not code. |
| Build order: the Fawateer side first, then the Mock POS page and the Hub | The mobile application is the main product; it can be shown and tested early with demo data. |

## Security and Privacy

| Decision | Why |
|---|---|
| The Hub signs each receipt with HMAC-SHA256 and a shared secret | Proves the request came from the Hub **and** was not changed on the way. |
| Mobile login uses JWT (Spring Security's built-in support, valid 24 h) | A standard approach with no extra library. |
| After 5 wrong passwords the account is locked for 15 minutes | Required by CLAUDE.md §9. A time lock unlocks itself, so no admin is needed. |
| Sensitive item names are encrypted with AES-256-GCM, one key per customer | Fawateer's server stores them but cannot read them; only the customer's phone can. |
| Keys are generated by PostgreSQL at start-up and pasted into the app from the Hub status page | No key is ever stored in the repository. This simulates key delivery during card linking (UC1, assumed). |
| The Hub removes the PAR, customer name, phone, and masked card number | Data minimization: Fawateer does not need them. |
| Scanned receipts are not encrypted | The customer uploads their own data. The Hub's encryption protects data that shops share about the customer. |
| The scan screen says that the photo is read by an AI service | An honest notice (PDPL); a free AI tier may use the data. |
| Encrypted item names cannot be searched on the server | This is proof that the server cannot read them. |

## AI

| Decision | Why |
|---|---|
| Gemini (free Flash model) through Spring AI; the model name is a setting in `.env` | The best Arabic text and receipt-photo reading, and no GPU is needed on the defense laptop. |
| Ollama + Gemma 3 4B only if Gemini causes problems | Keeps the project simple. |
| One category per receipt | The user can change it, and the change shows everywhere, including analytics. |
| Sensitive items never go to the AI; they use the shop's general category | Privacy. |
| The AI returns a period ("2 years"), and Java calculates the end date | AI models make arithmetic mistakes; Java does not. |
| Prompts are kept in separate files and must return strict JSON. Bad output gives `Uncategorized`. | Easy to show and improve. A receipt is never lost because of the AI. |

## Data

| Decision | Why |
|---|---|
| The schema is written in plain SQL files (`database/init`); JPA only checks it | The SQL files are the ERD and the data dictionary. |
| Consent time, FCM token, and notification switches are columns in `users` | One consent and one phone per user, so there are fewer tables. |
| Money uses `NUMERIC(12,2)` / `BigDecimal`. Prices exclude VAT; VAT = 15% of the subtotal, rounded half-up. | Exact halalas; matches the ZATCA invoice fields. |
| Time is stored as `timestamptz` and shown in Riyadh time. Weeks start on Sunday. | Correct dates around midnight; the Saudi convention. |
| Scanned photos are kept in a local `uploads/` folder; the database keeps the path | Matches CLAUDE.md §5.3. |
| Shop names are fictional | We have no permission to use real brands. |
| Seed dates are calculated from the current date | The charts always show "this month" and the last 6 months. |

## Mobile Application

| Decision | Why |
|---|---|
| One shared state object (`provider`); each screen loads its own data | Simple to explain; every screen follows the same pattern. |
| Translations use Flutter's built-in `gen-l10n` with ARB files | The official way; right-to-left works automatically. |
| A push that arrives while the app is open is shown as an in-app banner | No extra package is needed. |
| Two notification switches: new receipts (UC8) and deadline alerts (UC9) | UC8 and UC9 happen only when the user has them turned on. |

## Tools and Versions

| Decision | Why |
|---|---|
| Java 21, Spring Boot 3.5.x, Spring AI 1.1.x | The stack in CLAUDE.md, and the most documented versions. Spring Boot 3.5's free support ended in June 2026; moving to version 4 would be an upgrade, not a redesign. |
| PostgreSQL 17 and pgAdmin through Docker Compose | One command starts everything, and pgAdmin shows the databases in the demo. |
| Develop on the PC with the emulator; defend on a laptop with a real phone over a hotspot | Gemini needs no GPU. The hotspot provides both the local network and the internet. |
